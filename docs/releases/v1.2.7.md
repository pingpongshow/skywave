# Skywave v1.2.7 — Release Notes

A fix and feature release: broadcast voice, voice that keeps up with real
time, session keepalives, and the first tests of voice through the whole
modem. Skywave has never been released, so no compatibility constraint
applies, but **both ends of a link must run v1.2.7**: a new link frame
type (`BCAST_VOICE`) and voice now requires the voice capability on both
ends.

## What changed

### Voice

- **Broadcast voice.** `VOICE BROADCAST`, `VOICESTART`, `VOICEPTT ON|OFF`
  send one-way talkspurts without a session at `voice.broadcast_mode`, as
  `BCAST_VOICE` frames (link type 31). Any listening Skywave that is not
  in a session plays one out on its voice port, locked to one sender
  (`EVT:VOICE BCAST <tag>`, `EVT:VOICE BCAST END`, `BCASTRX=ON`). Before,
  `VOICE BROADCAST` only set a flag and `VOICESTART` failed.
- **Voice keeps up with real time.** Every voice unit is its own PHY
  frame, with its own preamble, sync and header (0.6-1.3 s on HF), so
  the old codec rule, which only checked the mode's NET rate, put most HF
  modes behind: WIDE M10 at 2400 aired 160% of the speech it carried.
  AUTO now picks the codec and the unit size (1-4 codewords, at most 3 s
  of speech) together so the airtime stays within 85% of the speech. It
  declines where nothing keeps up (NARROW, MID below M12); a manual
  `VOICECODEC` still runs there and `VOICESTATUS` reports `RT=NO`.
  Latency to first audio: 4-7 s on HF, 1-2 s on VHF-FM.
- **Voice capability enforced.** `CAP_VOICE` is advertised by voice
  builds and required on both ends; nobody set it before and nothing
  read it.
- **Settings and status.** `voice.codec` and `voice.broadcast_mode` are
  applied (they were parsed and ignored); `VOICESTATUS` adds `UNIT=`,
  `RT=` and `BCASTRX=`; `STATUS` reports `VOICE`, `CRYPTO` and `EPOCH`
  truthfully (they were hard-coded).

### Link

- **Keepalives.** They were built flag-gated in Phase 2 and the flag was
  never set, so an idle session with nothing else on the air died at the
  120 s idle timeout - every session with a pinned mode did. The
  initiator now probes a quiet link and the responder answers; neither
  probes while data moves, and the interval scales with the mode's frame
  airtime (PROTOCOL.md).
- `MODE` accepts M14 on VHF-FM.

### Floors

- CSS fading floors re-measured (same 48-curve campaign): every common
  point identical to the 2026-10-14 curves. Three entries are now set to
  what the derivation gives, after a fresh-seed check at floor+1 /
  floor+3: Good NARROW M0 -11.5 -> -12.0, Poor WIDE M2 NA -> 5.0, Poor
  ULTRA M1 1.5 -> 0.5.

## Voice through the whole modem (new tests)

| Scenario (`voice_st2`, two full modems) | Speech delivered | Similarity |
|---|---|---|
| CCIR Good 20 dB, M9 | 100% | 1.00 |
| CCIR Moderate 20 dB, M8 | 74% (fades lose whole units) | 0.87 |
| Static 24 dB, both directions, M10 | 100% / 100% | 1.00 |
| Encrypted, static 24 dB | 100% | 1.00 |
| VHF-FM CNR 30 dB, walking flutter / 700C | 100% / 100% | 1.00 |
| Broadcast, static / CCIR Good | 100% / 75% | 1.00 |

`st3_hardware`: 8.0 of 8.0 s of live voice through both TCP voice ports
over real audio devices. Similarity is the correlation with a local
Codec2 round trip of the same speech.

## Known limitations

- **Voice latency is seconds on HF.** Paying the preamble once per
  talkspurt would need PHY continuation frames; until then NARROW has no
  real-time voice and MID only from M12.
- Voice has not been tested on air or by a human listener (the test
  signal is a synthetic voiced buzz).
- VHF `M14` needs a data port flat below 300 Hz.
- Simulation and real-audio-device results; on-air confirmation is
  pending.
- No LICENSE file (owner's hold).
